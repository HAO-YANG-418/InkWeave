# 叙述口径（mask 掉对话）复核 —— 数据判决（2026-08-29）

> 起因：方案方提议「`texture_variety` 与「密度判空」两处都改为只统计叙述段（`p.type === 'narrative'`）」。
> 代码方按铁律先核机制真身、再跑数据，结论是**该提议要拆成两半：一半成立、一半被数据推翻**。
> 复现脚本：`_sandbox/_density_scan_narrative.mts`（全 47 章双口径分布）、`_sandbox/_check41_42.mts`（重点章明细）。

## 一、⚠️ 机制前提不成立：`p.type === 'narrative'` 在代码中不存在

| 核查项 | 结果 |
|---|---|
| 全树 grep `narrative` | 仅 `源码/cooling/generators/` 命中（模板渲染变量名），**与段落分类无关** |
| `TextStats`（`types.ts:460-471`） | 只有 `paragraphCount: number`，**无段落数组、无 type 字段** |
| `computeTextStats`（`checker.ts:329`） | `text.split(/\n+/)`，仅算 `paragraphCount` / `avgParagraphLength`，**不做叙述/对话分类** |

### 可行替代机制（已实现并验证）
不做 per-paragraph 分类，改为 **text-level mask**：复用代码中现成的 `checker.ts:354` `dialogueRegex`（即 `TextStats.dialogueRatio` 的同一口径），在统计前把引号内对话整段剥离。

```ts
const DIALOGUE_RE = /[""「」『』【】《》][^""「」『』【】《》]{1,}[""「」『』【】《》]/g;
const stripDialogue = (t: string) => t.replace(DIALOGUE_RE, '');
```
- 优点：无需新增数据结构、与现有 `dialogueRatio` 口径一致。
- 已知偏差：该 regex 含 `【】《》`，若正文用其标注书名/系统提示会被一并剥离。
- 实测剥离有效性：ch41/ch42/ch43 的引号字符数均 **100% 剥离**（36→0 / 146→0 / 102→0）。

## 四、判决 B：❌「密度判空」—— 叙述口径救不了，前提本身不成立

### B1. ch41「对话密集章」前提被推翻
方案方称 ch41 是对话密集章（审问陈默）导致密度被稀释。实测：
- ch41 引号字符仅 **36 个**、对话 **135 字 / 2107 字 = 6.4%**（叙述占比 **93.6%**，全样本最高档之一）。
- 剥对话后 CLI 五感/千字 **20.4 → 21.8**，几乎没动。
- **ch41 密度低不是被对话稀释，是叙述本身就稀。** 叙述口径对它无效。

### B2. 密度分支是死代码 —— 真正原因与对话无关
空心条件为 `sPerK < 25 && aPerK < 12`。实测**锚点/千字的最小值**：

| 口径 | 锚点/千字 min |
|---|---|
| CLI（全文） | 18.1 |
| CLI（叙述） | **19.4** |
| 源码（叙述） | **19.4** |

**`aPerK < 12` 在全样本中从未成立（min 19.4 > 12）→ `&&` 永假 → 该分支在两棵树中都是死代码。**
（注：两树锚点计数完全一致，只有五感词典不同。）

# 七、方案方补充：机制改用现成口径 + 标定表（2026-08-29）

## 7.1 机制更正：CLI 树 `p.type === 'narrative'` 存在，且已在用

§一 的 grep 查的是 `源码/types.ts`（**源码树** `TextStats`，确无 paragraphs）。但 CLI 树有个**同名不同类型**在 `检测工具/checkers.ts`：

| 位置 | 内容 |
|---|---|
| `检测工具/checkers.ts:30` | `export type ParagraphType = 'narrative' \| 'dialogue' \| 'mixed'` |
| `检测工具/checkers.ts:51` | CLI 树 `TextStats` **有** `paragraphs: ParagraphInfo[]` |
| `检测工具/checkers.ts:90` | `classifyParagraph()`：引号占比 >0.6 对话 / >0.3 混合 / 否则叙述 |
| `检测工具/checkers.ts:289` | **`checkCommaChain` 已在用该口径分流叙述/对话** |

→ **CLI 树不必用 text-level mask，照抄 `checkCommaChain:289` 两行即可**：

```ts
const narrativeText = stats.paragraphs.filter(p => p.type === 'narrative').map(p => p.text).join('\n');
```

顺带消掉 §六 第一个遗留：`【】《》` 误剥偏差不存在、不多一套 regex 口径。
**源码树**确无 per-paragraph type，那一侧才需要 §一 的 mask 方案。

> ⚠️ 项目老坑：两棵树的 `TextStats` **同名不同构**，核类型定义前先确认是哪棵树。

## 7.3 标定建议（方案方拍板）

1. **机制**：CLI 树用 `stats.paragraphs.filter(p.type==='narrative')`（照抄 `:289`）。源码树用 mask。
2. **阈值**：叙述口径下**维持 F=4 / T=6**，不额外放宽。（放宽到 F=6 只多消 4 章，却会漏掉 ch2「痒」这类真信号。）
3. **「凉」→ 走 U2 节点排除词表**，不靠数值阈值。
   - **理由（硬数据）**：`texture_variety` 属 **CLI 树**，而 U2 的 `threshold_overrides` **只喂源码树** → 数值阈值对它在架构上就够不着。
   - 且本节证明即便能调，排除凉（−7）也远优于调参（−4）。
   - **U2 解冻前**，凉会持续造成 7 章触发，属**已知且合理**——凉是核心概念词（克制残频的武器），高频是创作需要，不是写作缺陷。
