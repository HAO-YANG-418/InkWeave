# InkWeave 分支分类体系与现状检查报告

> 日期：2026-08-28 ｜ 代码方（已按铁律实跑核实，非照文档认）
> 背景：用户要求先搞清楚 InkWeave 这个 skill 的作用（"大众化、可多选、多分支风格的写作小说"），再说明书怎么分类、分支怎么用，然后检查，最后结合本会话既有结论（v2 检测器 / Item1 / 降噪 / ② 接 kb）给报告。

---

## 〇、先说结论（一句话）

InkWeave **不是"一个写作 skill"**，而是一套 **「1 个伞 + 3 个子 skill + 22 维知识库节点分支」** 的网文写作系统；书类型靠 **「平台 + 题材 + 风格维度」** 组合分类，用户用 **「预设（preset）」** 一键选一整套分支风格。检查显示分类体系完备、管道干净，但 **「检测树 vs KB 分支树尚未贯通（双树阈值分家）」**——这正是降噪工作该精准落地的点，而非"加能力"。

---

## 一、这个 skill 到底是什么（作用）

**伞定位**（写作工坊 SKILL.md 第 8 行）：*「你本身不绑定任何风格——加载哪个预设，就输出哪种风格。」*

| 层级 | 真身 | 职责 |
|---|---|---|
| 伞 | `InkWeave v4.8`（3 个子 skill 共用） | 通用网文写作引擎，风格由预设决定 |
| 子 skill 1 | `InkWeave写作工坊/SKILL.md` | 写前分析→生成→写后检查 三阶段执行 |
| 子 skill 2 | `InkWeave大纲创作院/SKILL.md` | 大纲/全书推演/情绪曲线/伏笔/质量门禁（15 步 + 5 门禁） |
| 子 skill 3 | `InkWeave设定工坊/SKILL.md` | 世界观/角色/力量体系/原创性隔离 |
| 共享层 | `源码/kb/nodes/`（22 维 95 选项）+ `知识库/预设/`（17 预设）+ `检测工具/` + `源码/` | 分支风格数据源 + 检测引擎 |

**"大众化、可多选、多分支风格"的落点**：用户不必懂写作理论，只需在大纲阶段选一个**预设**（如「玄幻修仙-起点V3.1追读版」「番茄2026追读版」），系统就自动加载对应 22 维分支组合，风格自现。这是它作为"可选多分支写作 skill"的产品形态。

## 二、书是怎么分类的（分类体系）

核实数：22 个节点维度、95 个选项（与 SKILL.md 声称的 "22节点×95选项" 一致，已 `ls` 实点）。分两大类：

### A. 书类型主轴（"这是什么书"）—— 2 个维度
| 维度 | 选项数 | 选项 | 含义 |
|---|---|---|---|
| `node_platform` 平台适配 | 7 | 番茄 / 起点 / 晋江 / 七猫 / 飞卢 / 新媒体 / 通用 | 发在哪个平台/App，决定读者偏好与算法指标 |
| `node_vocab_sensory` 感官/题材词汇 | 11 | 玄幻修仙 / 西方奇幻 / 科幻 / 悬疑推理 / 历史架空 / 军事战争 / 游戏竞技 / 都市 / 日常 / 灵异恐怖 / 通用 | 什么题材，决定专属词库与感官描写 |

### B. 风格分支（"这本书长什么样"）—— 20 个维度
视角(6) / 语调(7) / 句式节奏(4) / 段落密度(3) / 描写风格(4) / 修辞(4) / 战斗风格(4) / 情感表达(3) / 对话风格(4) / 锚点密度(4) / 开头冲击力(3) / 转折频率(3) / 章末钩子(3) / 爽点频率(3) / 信息密度(3) / 目标字数(5) / 严格度(3) / AI创意度(3) / AI续写长度(4) / 填充词(4)。

**组合方式**：每维选 1 选项 → 22 维交叉 = 天文数字组合。**预设**把这 22 维打包成 17 个命名风格（见 `知识库/预设/索引.md`，已实点 17 条全在）：
玄幻修仙-起点V3.1 / 玄幻修仙-番茄V3.1 / 都市异能-番茄V3.1 / 都市言情-晋江V3.1 / 悬疑推理 / 科幻-硬核 / 历史架空 / 灵异恐怖 / 武侠江湖 / 末日废土 / 轻小说 / 游戏竞技 / 游戏异界 / 西方奇幻 / 无限流 / 轻小说-日常 / 通用网文基础（默认）。

## 三、分支怎么用（使用机制）

**链路**（写作工坊 SKILL.md 阶段一/二 + 大纲创作院步骤0，已实读）：

1. **大纲阶段选预设**（大纲创作院 步骤0）→ 生成 `{项目}/书籍配置/{书名}.config.md`（22 节点选择表 + 显式文件路径 + 预设专属约束）。
2. **写章时加载**：写作工坊读 config → **只加载被选中的节点 .md**（不加载未选节点）→ 提取 `constraints` + `vocabulary` 注入生成上下文。
3. **双路径同源**（关键，已实读两处管道）：每个 `.kb.json` 含 `threshold_overrides: Record<string, number>`
   - **数值闸门路径**：`源码/config-merger.ts` **第4层（已实读 :191-199）** 把 `kb.threshold_overrides` 合并进 `Thresholds`（`thresholds = { ...thresholds, ...kb.threshold_overrides }`）→ 检测门禁用。
   - **写作教练路径**：`源码/compile-kb.ts` 把同一份 `threshold_overrides` 渲染成可读 `.md`（如 `知识库/节点/平台适配/番茄风.md` 的"数值参数"表）→ LLM 写作时加载。
   - 即 **单一真源 .kb.json，双路消费**，一致。
4. **切换预设**：说"换XX风格" → 重新生成 config → 22 节点全切换，需重跑写前分析。

**两个真身节点 schema 验证**（已读原始 .kb.json）：
- `opt_platform_tomato`（番茄风）：`threshold_overrides` 满（maxParagraphLength:80、minDialogueConflictRatio:0.3 等 12 项）+ `radar_weights` + `constraints` + `examples` 全 → 平台维靠**阈值+教练**双驱动。
- `opt_vocab_xianxia`（玄幻修仙词汇）：`threshold_overrides` **为空**，只有 `vocabulary.add`（丹田/灵气/飞剑…）+ `constraints` → 题材维靠**词库注入**而非阈值驱动（证明分类维度驱动方式不同，非一刀切）。

## 五、结合本会话既有结论的洞察（v2 / Item1 / 降噪 / ②）

1. **降噪的"不盲放宽"决策，与分类体系严丝合缝。**
   我前一轮拒绝盲放宽 `质感多样性` 全局常量（"凉"是裂日冷感基调刻意复用），当时判断"应归 per-work 校准"。现在看，这套 **22 维 KB 节点系统正是 per-work 校准的天然载体**：把"凉"的合法复用归到「玄幻/冷感题材节点」在该节点放宽，而非全局放宽伤害其它作。分类体系 = 降噪的精准落点。

2. **"双树阈值分家"（你早先诊断③）的真身坐实。**
   - 源码树门禁：理论上可借 `config-merger` 第4层吃 KB 节点 `threshold_overrides`（管道已实读存在）。
   - CLI 树（`检测工具/checkers.ts`）：执行器只传 `fn(text, stats)`、**不传 thresholds** → 吃硬编码常量。
   - 所以 `质感多样性/碎句/锚点` 等告警在 CLI 树是写死的，与 KB 分支无关。降噪若只动全局常量，恰恰违背这套 kb 架构。

3. **② 消硬编码主角名的决策被分类体系印证。**
   因 `threshold_overrides` 不能载字符串，我改走 `project.json`（per-work）。同理，未来所有 per-work 参数应优先挂 **KB 节点 / 项目配置**，而非新增硬编码——与"分类驱动"哲学一致。

4. **Item1 检测器尚未接入分支体系。**
   `dialogue_conflict` / `protagonist_stakes` 目前也只吃硬编码常量/函数内逻辑。若未来要"不同平台对话碰撞标准不同"（晋江偏情感碰撞、番茄偏信息反咬），正确做法是让检测器读 KB 节点的 `threshold_overrides`，而非再写一套 `if`——**但这需要 U1 管道贯通（见 §六），而 U1 已打回冻结、非零新架构风险，不能算"复用已验证管道零风险"**。

---

## 六、结论与优先级建议（交你拍）

- **引擎没退化**；分类体系完备（22 维 95 选项 + 17 预设）；分支使用机制清晰；管道本身干净（单一真源 .kb.json、双路消费一致）。
- **真正值得动的不是"加能力"，而是"把检测树接入 KB 分支树"**：让 CLI 树检测阈值从书籍配置/KB 节点灌入，把 by-design 的题材复用归到对应节点校准。这会是降噪的"精准版"。**但此项正是 U1，已打回冻结（详见 `InkWeave_后续升级方案_2026-08-28.md` §三 P0）：CLI 树执行器只传 `fn(text, stats)`、`check-chapter.ts:28` 故意不接 mergeConfig，要让其吃 KB 阈值必须改执行器透传或 import mergeConfig，均为真改动、非零新架构风险；且 U1 治不了 D2（`TEXTURE_WORDS` 是词表非阈值）。故 U1 不当"优先做"，等真需跨作阈值再开。**
- 建议优先级（与升级方案报告对齐）：
  1. **先做 U2 题材节点级校准** → "凉"等合法复用归题材节点（`threshold_overrides` 仅载数值阈值 `Record<string, number>`，故只能校准数值类过敏项；`TEXTURE_WORDS` 词表类 D2 仍走 Y 降噪全局兜底，见下方注）。
  2. **U1 检测树吃 KB 阈值：冻结**，等真需跨作阈值再开（非零风险、治不了 D2）。
  3. **LLM 语义层**等真 LLM 环境再解冻（本会话已冻结标实验接口）。

> 注（U2 真实边界，不假装一把梭）：`threshold_overrides` 是 `Record<string, number>`，只能挂数值阈值（如 `sense_density` 字数下限、`texture_variety` 频次），**无法承载 `TEXTURE_WORDS` 字符串词表**。因此"凉"被 `TEXTURE_WORDS` 误伤的 D2，U2 节点级校准无法直接消解，仍需 Y 降噪（全局频次 3→4 放宽）作兜底，或后续另立"节点级排除词表"机制。这是 U2 设计时要直面的约束。

> 注：本会话已落地项（Item1 双检测器 + LLM 层冻结 + 降噪对齐/双计修复 + ② 主角名接 project.json）均独立于上述"检测树接 KB"贯通工作，互不冲突；贯通是下一步、且风险最低的方向。
