## 0. 为什么需要这份方案（治同一个洞）

R3 接线让生成循环能读「本张检测的 checker error」并触发重写。但**跨章**的反向闭环（上章犯过的错、下章别再犯）仍断在生成循环之外：

- 闭环1（`检测工具/` 离线闭环）只做「生成完→检测→存指纹→下次 CLI 侧注入写前分析」，**不进 gwe-engine 生成循环**。
- 闭环2（`源码/learning/`）只吃**手动编辑**反馈，不碰 warning/检测指纹。
- 闭环3（v2 ②-C 设想的 `prompt-builder.ts:324`）路径真实存在，但**没接**。

所以「上章指纹 → 生成时被遵守」这层三套闭环都没做。它与 R3 治的是**同一个断点**（生成时信号是死胡同），应合并成一个「生成自纠闭环」一次性补。本文是这层的落地方案。

- ⚠️ **关键校正（2026-08-24 用户 fact-check）**：第[4]层 userCustomPrompt **确实存在**（在 GWEEngine 类里），但 **orchestrator 实际生成链路根本不调 `GWEEngine.buildSystemPrompt`**——它走的是 `engine.ts` 对象字面量的 `buildMessages` → `buildWritingMessages`（context-builder.ts），后者不读 `userOverrides.prompt`。故"第[4]层不存在"表述不准；准确说法是"第[4]层在 GWEEngine 类存在、但 orchestrator 不用，对 orchestrator 生成是死通道"。

### 1.2 当前是死通道（证实"闭环1 没接生成循环"）✅
- grep `源码/writing/orchestrator.ts` 全空 `setCustomPromptText` / `userOverrides` —— orchestrator **完全不碰** `userOverrides.prompt`。
- 即生成链路里第[4]层永远 undefined，除非外部手动调 `setCustomPromptText`。
- **真实生成通道**：`engine.ts` 对象字面量 `buildMessages`（:281 起）→ `buildWritingMessages`（context-builder.ts:690），通过 `dynamicSections` 把每章变化内容（含上章禁忌）注入 **user message 动态区**（:831-836），不进 system prompt（system prompt 固定以便 API 前缀缓存）。

### 1.3 多轮生成都带禁忌（真实通道动态区版可行）✅
- `buildWritingMessages` 的 `dynamicSections` 在每次 `buildMessages` 调用时重建（:833 拼入 user message）。
- `orchestrator.ts` 多轮（`generateWithReflection` 的首生成 / 钩子重写 / 弱维度修复 / 兜底重写）均复用同一 `buildWritingMessages` 通道，故 `prevChapterTaboo` 注入后各轮 user message 都带禁忌。
- 插桩点设在 `writeChapter` 调 `generateWithReflection` 之前（:417-428），用 `setPrevChapterTaboo` 设引擎内存态，由 `buildMessages` 取走传入 `buildWritingMessages`。

### 1.4 插桩点唯一 ✅
- `orchestrator.ts:417`：`writeChapter` 调 `generateWithReflection(messages, intent, request)` 之前，是唯一的「每章生成前」钩子。在此加「读上章指纹 → 转禁忌 → setPrevChapterTaboo」。

### 1.5 闭环1 指纹格式已知 ✅
- `检测工具/check-chapter.ts:286-342` 写 `*.fingerprint.json`，字段含：`errors` / `warnings` / `stylePatterns`(verbStacking/nameStacking/deDensity) / `facts`(ChapterFact) / `semanticSummary`。

## 2. 方案选型（修正 v2 文档措辞）

v2 文档 ②-C 写「做法一零改 prompt-builder」——**实测修正**：prompt-builder 零改，但 orchestrator 要加「读指纹→转禁忌→setPrevChapterTaboo」逻辑（约 15-20 行，含项目目录定位 + 容错）。做法二（新增 [4.5] 层）反而要改 prompt-builder + 改 gwe-engine 传参，更重。

**拍板：做法一自动版**（复用真实通道：`setPrevChapterTaboo` → `buildWritingMessages` 的 `dynamicSections`（user message 动态区）+ orchestrator 插桩），理由：
- 零改 prompt-builder（低风险）。
- 复用闭环1 已成熟的 fingerprint 格式与 pre-analysis 的禁忌转写逻辑。
- 多轮生成天然带禁忌，无需改 callLLM。

### 3.2 orchestrator 插桩（`源码/writing/orchestrator.ts`）

## 5. 风险与回滚

- **风险1（路径错位）**：`projectDir` / 文件名拼错导致读不到指纹 → 静默降级（无禁忌注入），生成照常、只是没闭环。不阻断，但功能失效。→ 回滚 = 注释插桩块。
- **风险2（禁忌噪声）**：指纹转写过长/含低频 warning → system prompt 被污染、生成质量下降。→ 回滚 = 收紧 `fingerprintToTabooText` 的 cap 与 TopN。
- **风险3（跨章污染）**：orchestrator 复用 + 不清内存态 → 下一章带本章禁忌。→ **已按 #5 根堵**：插桩「始终重置」`setPrevChapterTaboo`（有指纹注入、无指纹清空），见 §3.2/§4 #5。
- **回滚总开关**：可在 `config` 加 `enableFingerprintInjection: boolean`（默认 true），关闭即跳过插桩，零代码回滚。
