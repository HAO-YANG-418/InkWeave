## 四、✅ 已拍板并实施：源码树 R4 同步套用方案 B（2026-08-29，用户"你看着办"授权）

**决策理由（双树必须自洽）**：CLI 在 2100 卡、生成树在 2000 放行，等于引擎会稳定产出"刚生成就被验收打回"的章节（ch38 即实例：1541 字生成通过、验收不合格、人工补写至 2124）。R4 注释自述「治本写空，经 R3 接线逼自纠」，而它从不触发——这是 bug 不是设计。

### 4.1 改动清单（3 处）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `源码/checker.ts:55-92`（R4） | 分层门禁：`totalWords < r4Min` → error 不论密度（ruleId `word_count_hollow`）；`r4Min ~ 0.9×目标` → 密度口径 `sPerK<25 && aPerK<12` 判空；**删除恒 false 的 `sensoryTotal<3 && anchorCount<3`** |
| 2 | `知识库/阈值标定/default.json:52` | `minChapterWords: 2000 → 2100`（**标定源**，与验收下限 0.7×3000 对齐） |
| 3 | `源码/types.ts:220` | `DEFAULT_THRESHOLDS.minChapterWords: 2000 → 2100`（代码兜底同步）；`:143` 注释同步更新（旧注释"短而密放行"已作废） |

> 为何必须改标定源：R4 优先读 `thresholds.minChapterWords`，而 KB 已标定 2000 且会覆盖代码默认值——只改代码不生效。改标定值同时符合项目「③ 2E 单一标定源」方向，后续调参无需动代码。
> `r4Min` 无 KB 配置时的回退值由 `2000` 改为 `Math.round(r4Target * 0.7)`（默认 2100）。

### 4.3 ⚠️ 新暴露的口径差（观察项，未处理）

两棵树的感官词典不同（CLI 用 `visual/auditory/tactile/olfactory/gustatory`，源码树用 `sight/sound/smell/touch/taste`），**同一章算出的五感密度不一致**：

- ch38：CLI 41.4/千字 **vs** 源码树 68.7/千字（约 1.7 倍）

而 `sPerK < 25` 这个阈值是按 **CLI 口径**标定的（方案文档 §二 的密度分布来自 CLI `_density_scan.mts`）。**同一个 25 在源码树里宽松得多**，即源码树的"空心"判定实际比 CLI 更松。

- 影响范围：仅「2100–2700 密度豁免区」的判空；本次 6 章 error 均走"低于硬下限不论密度"分支，**不受此影响**。
- 若要严格对齐，需单独标定源码树的密度分布（另跑一次源码树口径的 density scan），属标定工作，本轮未做。

## 六、结论

- **方案 B 已按规格实施完毕，构建通过，三/四段验证全绿。**
- **「不误伤 2100+ 章」关键假设成立**（ch1–31 零误伤、ch38–47 零误伤）。
- **对外口径**：旧规则下全绿是规则失效的虚假全绿；新规则下 6 章因写空如实报错（非回归失败，是检测器开始干活）。
- **源码树 R4 已同步套用方案 B**（见 §四）：生成时自纠现在能拦写空，双树口径一致。改动含代码 1 处 + 标定源 1 处 + 默认值 1 处。
- **行为影响提醒**：生成路径现在会对 <2100 字的章触发重写轮次（受 `maxRewriteRounds` 限制）——这是 R4 原本的设计意图，但意味着后续生成短章会多消耗轮次，属预期成本。
- **遗留观察**：两树感官词典不一致导致同一 `sPerK<25` 在源码树里更宽松（§4.3），需单独标定源码树密度分布才能严格对齐，本轮未做。
