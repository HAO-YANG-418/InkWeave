## 一、本补实回答的问题

Item1 落地报告 §五 已知限制列了四条，本补实只针对 **③ LLM 语义层未实现**。

正则层盲区回顾（方案方 §⑫ 发现的真问题）：
- 无引号对话（"周野回头，眼神钉他。你尝到什么。"）→ 无引号轮次提取靠「角色名+言语动词」锚点，纯上下文无动词则漏检。
- 主角私心靠词表硬匹配，语义层"为个人赌而非为任务"的微妙动机词表覆盖不全。

LLM 语义层用一个**单次调用**同时判 `collision`（对话碰撞）+ `stakes`（主角私心）两个语义维度，补全上述盲区。

## 二、落地内容（真身位置）

### 1. 新建 `源码/checks/check-dialogue-semantics.ts`
- `export async function checkDialogueSemantics(text, llm, thresholds?)`
- **降级安全**：`if (!hasLLM(llm)) return []`——无 LLM 配置静默返空，绝不阻断生成（与 `checkSemanticSmoothness` 同范式）。
- **单次 LLM 调用**：prompt 要求模型判两维度 → 输出纯 JSON `{hasDialogue, collision, collisionEvidence, hasStakes, stakesEvidence}`，经 `llmJson` 解析（复用 `llm-helper`，结构化兜底）。
- **违规构造**：
  - `hasDialogue && !collision` → `dialogue_collision_llm`（对话缺乏碰撞·语义层，warning）
  - `!hasStakes` → `protagonist_stakes_llm`（主角工具人·语义层，warning）
- **对齐口径**：独白/无对话章 `hasDialogue=false` 跳过碰撞判定；`minCount` 读 `thresholds.dialogueConflictMinCount ?? 4`，与正则层跳过阈值一致。
- **截断护栏**：正文超 6000 字只喂前 6000（防 token 溢出），属保守值，长章可后续调。

### 2. `源码/checks/index.ts` 注册导出（line 27）
```
export { checkDialogueSemantics } from './check-dialogue-semantics';
```

### 3. `源码/reflection/engine.ts` 接入 `reflectAsync`（line 22-23 import / 589-596 调用 / 646-656 concerns 并入）
- 调用段（紧接 D-SMOOTH 之后）：
  ```ts
  let semanticViolations: RuleViolation[] = []
  try {
    semanticViolations = await checkDialogueSemantics(input.content, this.llm)
  } catch (e) {
    logWarn('Reflection', 'LLM 语义层（对话/私心）检测异常，降级跳过', e)
  }
  const mergedViolations = [...(checkerViolations ?? []), ...smoothnessViolations, ...semanticViolations]
  ```
- **concerns 并入**（warning 级驱动自纠、不硬拦门禁）：
  ```ts
  for (const v of semanticViolations.filter(x => x.severity === 'warning')) {
    allConcerns = [...allConcerns, {
      dimension: 'rule_check' as QualityDimension,
      severity: 0.45,
      description: `[检测期违规 ${v.ruleId}] ${v.message}`,
      suggestion: v.suggestion ?? '按检测建议修正',
      location: undefined,
    }]
  }
  ```
- **门禁安全论证**：`passed = overallScore >= qualityGate && !hasCheckerError`（engine.ts:659）。`hasCheckerError` 仅由 `severity==='error'` 的违规触发（line 633），本层两违规均为 `warning`，**不触发 `hasCheckerError`**，故不硬拦门禁；但 `allConcerns` 含本层 warning → 驱动生成自纠循环（重写）。这正是"驱动自纠但不硬拦"的设计意图。
- 与 R3 接线（line 630-644）并存，互不干扰：R3 处理 error 级硬拦，本层处理 warning 级软纠。

## 四、诚实标注（沿用 §⑩/§⑬ 口径）

1. **live LLM 路径未实跑**：本环境无 LLM 配置，仅验证了"无 LLM → `[]`"的降级确定性路径。live 语义判定（对话碰撞/私心识别是否真准）需在配置 LLM 的环境回归，本轮不作真实性背书——与 §⑩"评分来自非确定性评分器未重跑"的诚实原则一致。
2. **正则层仍是门禁权威源**：本语义层是 `reflectAsync` 路径的**生成时增强**（warning 级软纠），不进入同步 `check()` 门禁；CLI 门禁权威源仍是 Item1 落地的正则双检测器。两路互补，无冲突。
3. **不阻断门禁**：两违规均 warning 级，符合 Item1 落地时已拍板的"先 warning 观察"策略。
