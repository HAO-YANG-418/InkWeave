## 0. 为什么现在做、为什么能做成

### 0.1 现有缺口（已核实两套代码树）

> **代码树分治（2026-08-22 校正）**：工作区存在两套并行代码——  
> - **`检测工具/`**：实战回归真正跑的检测器（`checkers.ts` / `check-chapter.ts` / `check-all.ts`），用户上轮改 D1–D6 用的就是它。D2 实现在此（第 732–735 行）。  
> - **`源码/`**：引擎本体（`prompt-builder.ts` 生成器、`learning/feedback-loop.ts` 学习器、`checks/check-*.ts` 是另一套检测器口径，与实战链路不一致）。  
> 本闭环的检测侧接 `检测工具/checkers.ts`，生成注入侧接 `源码/prompt-builder.ts`（第 [4] 层）。

- `检测工具/checkers.ts` 每章产出 `RuleViolation[]`（类型定义第 64 行），字段：`ruleId` / `ruleName` / `message` / `severity`（error|warning|info）/ `suggestion`。**这些是结构化信号，但跑完即弃**（第 1424 行 `warnings` 仅用于统计，未回写）。**
- `源码/prompt-builder.ts` 的 7 层拼装里，**第 [4] 层 `userCustomPrompt`** 是"用户自由文本自定义规则，直接拼到 system prompt"——天然是注入"本章禁忌"的落点，目前只接人工输入。
- `源码/learning/feedback-loop.ts` 的 `FeedbackLoop` **只吃"用户对正文的手动编辑"**（`recordEdit`），不吃"检测器的结构化 warning"。这是 08-17 报告说"反向闭环未打通"的真正原因——学习的入口错了。
- 持久化不依赖 `源码/memory/index.ts` 的 `LongTermMemory`——`检测工具/checkers.ts` 第 1115 行已有项目内跨章状态通道，本闭环复用它即可（见 3.2）。

### 0.2 结论
缺口不在"缺模块"，而在**缺一根连线**：检测器输出 → 持久化 → 下一章生成注入。本方案就是这根连线，尽量复用现有接口，不重写架构。

## 1. 闭环数据流（端到端）

```
check-chapter 跑完第 N 章
        │
        ▼
[新增] extractWarnings(violations)          ← 取 severity==='warning' 的 Top3 ruleId
        │
        ▼
[新增] buildTabooPrompt(topWarnings, N)     ← 转自然语言禁忌文本
        │
        ▼
[复用] LongTermMemory.remember()            ← 持久化到 nextChapterTaboos(项目级)
        │
        ▼
第 N+1 章 buildSystemPrompt() 时
        │
        ▼
[改动] 第 [4] 层 userCustomPrompt 拼接 taboo 文本  ← 注入"本章禁忌"
        │
        ▼
生成正文 → 检测器再跑 → 更新禁忌（衰减旧项、增补新项）
```

闭环形成：第 N 章犯的 warning，第 N+1 章被显式禁止，第 N+2 章若已不犯则自然衰减。

## 2. 新增模块：`源码/learning/warning-feedback.ts`

> 纯函数 + 一个轻量状态读写，不依赖 LLM，零新增运行时风险。

### 2.1 导出 API（给代码方落地）
```ts
// warning-feedback.ts
import type { RuleViolation } from '../types'
import { LongTermMemory } from '../memory'  // 复用现有

export interface ChapterTaboo {
  chapterNumber: number
  ruleId: string
  ruleName: string
  suggestion: string
  weight: number      // 命中次数累加，用于衰减
  lastSeen: number    // 章号，用于滑动窗口
}

/** 从一章的 violations 提取 warning Top3（按出现次数/严重度排序） */
export function extractTopWarnings(
  violations: RuleViolation[],
  limit = 3
): RuleViolation[]

/** 把 warning 列表转成可注入的自然语言禁忌文本 */
export function buildTabooPrompt(taboos: ChapterTaboo[]): string

/** 更新项目级禁忌表：合并新 warning，衰减超过 W 章未命中的旧项 */
export function upsertTaboos(
  mem: LongTermMemory,
  projectId: string,
  chapterNumber: number,
  warnings: RuleViolation[]
): ChapterTaboo[]

/** 读取下一章应当注入的禁忌（已衰减过滤） */
export function loadNextChapterTaboos(
  mem: LongTermMemory,
  projectId: string,
  nextChapterNumber: number
): ChapterTaboo[]
```

### 2.2 关键参数（方案方建议默认值，代码方可调）
| 参数 | 值 | 说明 |
|------|-----|------|
| `TOP_N` | 3 | 每章最多注入 3 条禁忌，避免 prompt 噪音 |
| `DECAY_WINDOW` | 4 | 某 ruleId 超过 4 章未再命中，权重衰减 50% |
| `DROP_THRESHOLD` | 0.5×base | 衰减后权重低于阈值则从禁忌表移除 |
| `severity 过滤` | 仅 `warning` | `error` 由门禁硬卡不需注入；`info` 忽略 |

### 2.3 禁忌文本模板（注入第 [4] 层）
```
【上一章自检提示·本章请规避】
- 避免"不是X是Y"句式堆砌（上一章触发2次）：直接写Y的具体表现，别绕弯子。
- 控制碎句：上一章连续短句偏多，无身份短句请合并到前后句。
- 触觉词"凉/冷"出现频次偏高，本章换听觉/嗅觉锚点调剂。
```
> 模板由 `buildTabooPrompt` 按 `ruleName` + `suggestion` 自动拼接，**不写死具体章号以外的任何内容**。

在 `buildSystemPrompt` 的 [4] 层（`userCustomPrompt` 拼接处）**之后**，追加：
```ts
// [4.5] 反向闭环：注入上一章自检禁忌
if (options.nextChapterTaboos && options.nextChapterTaboos.length > 0) {
  const tabooText = buildTabooPrompt(options.nextChapterTaboos)

```

### 3.2 `检测工具/checkers.ts`（实战回归真正跑的检测器，非 `源码/` 那套）

> **代码树对齐说明（2026-08-22 校正）**：本闭环对接的检测器是 `检测工具/checkers.ts`——即用户上轮改 D1–D6、跑第17–25章回归用的那套，口径才是真实的。原方案误写为 `源码/checker.ts` / `源码/checks/check-*.ts`，那套（`源码/checks/check-not-shi-pattern.ts` 的 D2 是 `> 2 ? warning`、约第24行）与实战回归链路不一致，**不是本闭环的对接对象**。
> `RuleViolation` 类型定义在 `检测工具/checkers.ts` 第 64 行；warning 产出在第 1424 行 `violations.filter(v => v.severity === 'warning')`。

在每章检测完成、`violations` 汇总之后（约第 1423–1425 行 errors/warnings/infos 拆分处）调用：
```ts
const warnings = extractTopWarnings(violations)
upsertTaboos(mem, projectId, chapterNumber, warnings)
```
并在"开始下一章生成"前（check-chapter 主流程调用 `buildSystemPrompt` 处）调用：
```ts
const taboos = loadNextChapterTaboos(mem, projectId, nextChapterNumber)
// 传入 buildSystemPrompt 的 options.nextChapterTaboos
```

**跨树接缝方案（2026-08-23 校正）**：`检测工具/checkers.ts` 为扁平单文件实战检测器，**无"第1115行跨章通道"**（第1115行实为 `checkWordCountTarget`，原引用作废）。本闭环的"取 warning"从 `检测工具/checkers.ts` 的 `checkChapter` 返回值取，"注入"写到 `源码/prompt-builder.ts` 第[4]层；两树不直接硬连，用中间文件 `nextChapterTaboos.json`（项目级）解耦传递禁忌表，避免双树耦合。接口语义不变：warning Top3 → 下一章注入。

### 3.3 不改动的部分
- `检测工具/checkers.ts` 内各检测器逻辑（D1–D6 已修）：**不动**。反向闭环只在主流程尾端"读取 warning + 持久化 + 下一章注入"，不修改任何单条检测规则。

## 4. 防副作用设计（必须看）

1. **只注入 warning，不注入 error**：error 由门禁卡死，注入会重复惩罚导致生成退化。
2. **Top3 上限 + 衰减**：避免禁忌越积越多把 prompt 撑爆，也避免"一次性毛病"被永久记仇。
3. **自然语言而非硬约束列表**：禁忌用"请规避/调剂"措辞，与铁则的"禁止"区分层级，不污染契约语义。
4. **项目级隔离**：`projectId` 维度存，裂日项目的禁忌不串到矿工项目。
5. **可关闭**：`mergedConfig` 加 `reverseLoopEnabled: boolean`（默认 true），抖音卖课用户可在 UI 一键关。

## 附：为什么不用现有的 FeedbackLoop 直接吃 warning

`FeedbackLoop.recordEdit` 需要 `originalContent` / `modifiedContent` 两份全文做 diff，且学习依赖 `minEventsForLearning`（默认要攒够事件才 learn）。把结构化 warning 塞进"正文 diff"语义是错的——warning 是检测器结论，不是用户编辑意图。平行建 `warning-feedback` 比改造 `FeedbackLoop` 更干净、风险更低、语义更准。**本期不耦合两条学习线。**
